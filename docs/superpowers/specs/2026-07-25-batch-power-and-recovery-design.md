# 批量任务息屏保活与断点恢复设计

## 背景

当前批量评论任务由 `batch.html` 中的 JavaScript 状态机调度。任务开始后，队列、当前索引、活动标签页和大部分统计仅保存在页面内存中。`chrome.storage.local` 虽然保存了部分设置和最近结果，但不足以在 Chrome 重启、批处理页刷新或页面被丢弃后重建完整批次。

插件也没有申请 `power` 权限。Mac 自动进入系统睡眠后，Chrome、网络请求、页面定时器和内容脚本都会停止，只有关闭显示器而系统仍保持唤醒时才能继续运行。

本功能保留现有 `batch.html` 调度架构，增加后台电源管理和完整的批次检查点。Chrome 重启后自动打开恢复页，但必须由用户确认后才继续提交评论。

## 目标

- 批量任务开始或从暂停状态继续时，请求 `chrome.power.requestKeepAwake('system')`。
- 允许显示器按系统设置关闭，同时阻止因用户闲置导致的系统睡眠。
- 批量任务暂停、终止、完成或扩展卸载时，不再保留本批次的唤醒请求。
- 持久化重建批次所需的完整输入、进度、逐项结果、运行设置和当前任务阶段。
- Chrome 重启后自动打开一个批处理恢复页，显示中断批次，但不自动继续。
- 用户点击“继续处理”后从安全断点恢复未完成队列。
- 对中断时可能已经提交、但尚未收到确认的项目采取保守策略，避免自动重复评论。
- 批处理页刷新或被 Chrome 丢弃后，使用相同的暂停恢复流程。

## 非目标

- 不把完整队列调度器迁移到 Manifest V3 service worker。
- 不支持一个 Chrome 配置文件同时运行多个独立 CSV 批次。
- 不在系统重启或断电后绕过登录自动启动 Chrome。
- 不保证第三方网站、网络、AI 服务或 Chrome 自身永不崩溃。
- 不自动重试处于“可能已经提交”状态的项目。
- 不改变评论框识别、文案生成、非法站点过滤或 CSV 导出业务规则。

## 用户体验

### 正常运行

用户点击“开始处理”后，页面照常执行批次。插件在后台请求 `system` 级别保活。显示器可以息屏，Mac 仍保持运行。

任务页面显示“系统保持唤醒中”。暂停、终止或完成后，该提示消失，插件释放保活请求。

### Chrome 重启后

如果 Chrome 启动时发现未结束的批次：

1. 后台把批次转换为 `paused_recovery` 状态。
2. 后台释放任何保活状态，不在用户确认前重新申请。
3. 如果尚未打开批处理页，则自动打开 `batch.html`。
4. 页面恢复 CSV 名称、完整行数据、设置、进度、统计和已有结果。
5. 页面显示“上次任务异常中断，已暂停恢复”及“继续处理”按钮。
6. 只有用户点击“继续处理”后，才重新申请系统保活并调度剩余项目。

如果用户选择终止，已有结果继续保留并可以导出，未处理项目不再自动执行。

### 页面刷新或丢弃后

批处理页重新加载时读取持久化检查点。若检查点仍标记为运行中，新页面不得直接继续，而是先转换为 `paused_recovery` 并要求用户确认。

## 架构

### 1. 后台电源管理器

`manifest.json` 增加 `power` 权限。所有 `chrome.power` 调用集中在后台 service worker 中，批处理页不直接控制电源。

后台接受以下会话命令：

- `BATCH_SESSION_START`：创建检查点并请求 `system` 保活。
- `BATCH_SESSION_RESUME`：把暂停批次改为运行中并请求 `system` 保活。
- `BATCH_SESSION_PAUSE`：保存暂停状态并释放保活。
- `BATCH_SESSION_STOP`：保存终止状态并释放保活。
- `BATCH_SESSION_COMPLETE`：保存完成状态并释放保活。

后台维护进程内布尔值，避免对同一状态重复调用 Power API。状态以持久化批次为准：

- `running` 才允许保持唤醒。
- `paused_recovery`、`terminated` 和 `completed` 必须释放保持唤醒。

Manifest V3 service worker 被挂起不等同于扩展卸载，已经申请的保活由 Chrome 管理。若后台重新加载并收到运行批次的任一消息，它会再次幂等地确认 `requestKeepAwake('system')`。

### 2. 持久化批次检查点

新增单一存储键 `batchRuntimeCheckpoint`，结构版本为 1：

```js
{
  version: 1,
  batchId: 'uuid',
  status: 'running',
  createdAt: 0,
  updatedAt: 0,
  source: {
    fileName: 'input.csv',
    headers: [],
    rows: [],
    parsedUrls: []
  },
  settings: {
    autoOpenPanel: false,
    autoGenerate: false,
    autoSubmit: false,
    timeoutSeconds: 60
  },
  cursor: {
    nextIndex: 0
  },
  tasks: {
    '0': {
      urlIndex: 0,
      state: 'queued',
      phase: null,
      tabId: null,
      startedAt: null,
      updatedAt: 0
    }
  },
  results: []
}
```

`source.rows` 和 `source.parsedUrls` 保存完整批次，不使用现有“最近 100 条”截断规则。活动检查点必须能恢复整个输入文件；现有 `batchResults` 和 `batchLocalResults` 继续承担兼容和历史结果用途。

任务状态为：

- `queued`：尚未开始或可以安全重试。
- `active`：正在打开页面、识别表单或生成文案。
- `submitting`：即将点击提交，或已经点击但尚未得到终态确认。
- `terminal`：已有最终结果，不再调度。

批次状态为：

- `running`
- `paused_recovery`
- `terminated`
- `completed`

检查点在以下边界写入：

- 批次创建后、打开第一个标签页前。
- 领取一个 URL、创建标签页和进入提交阶段时。
- 收到每个终态结果时。
- 当前索引、统计、设置或活动任务发生改变时。
- 暂停、恢复、终止和完成时。

### 3. 单写入者与状态命令

后台 service worker 是检查点的唯一写入者，避免 `batch.html`、内容脚本和后台并发覆盖整个对象。

批处理页和内容脚本发送语义化状态命令，后台从 `chrome.storage.local` 读取当前检查点、应用纯状态转换、写回并返回更新后的检查点。后台用进程内 Promise 队列串行化同一批次的写操作；service worker 重启后以存储中的最新检查点继续。

纯状态转换放在独立 ES module 中，不依赖 Chrome API 或 DOM，以便使用 Node 测试覆盖。

后台拒绝以下更新：

- `batchId` 与当前检查点不一致。
- 已为 `terminal` 的任务再次写入结果。
- 终止或完成批次尝试恢复为运行中。
- 缺少任务身份或 URL 索引越界。

### 4. 提交阶段信号

内容脚本在真正点击提交按钮之前，先向后台发送 `BATCH_TASK_SUBMITTING`，并等待检查点写入成功。写入失败时不得继续点击提交按钮，而应上报失败，避免出现无法判断是否提交的状态。

提交确认仍沿用现有 `BATCH_HANDLE_CONFIRM` 流程。后台在持久化最终结果时，同时把对应任务改为 `terminal`。

普通识别、生成或填写阶段保持为 `active`。这些阶段中断后没有发生评论提交，可以安全回到 `queued`。

### 5. 中断归一化

Chrome 启动或批处理页恢复时，后台对遗留的 `running` 检查点执行一次归一化：

- `queued` 保持不变。
- `active` 改回 `queued`，清除旧 `tabId` 和开始时间。
- `submitting` 改为 `terminal`，追加结果：

```js
{
  result: 'manual_required',
  errorMessage: '任务在提交确认前中断，评论可能已提交，请人工确认'
}
```

- 已有终态结果保持不变。
- 批次状态改为 `paused_recovery`。
- `cursor.nextIndex` 重新指向第一个没有终态结果的任务。

该转换必须幂等。多次启动、刷新或重复恢复不会重复追加人工确认结果。

### 6. 启动恢复与页面重建

后台监听 `chrome.runtime.onStartup`：

1. 读取检查点。
2. 如果批次已经 `completed` 或 `terminated`，不打开页面。
3. 如果批次为 `running`，执行中断归一化。
4. 查询是否已经存在扩展的 `batch.html` 标签页。
5. 不存在时创建一个恢复页；存在时不重复创建。

`batch.html` 初始化时主动读取检查点。发现 `running` 状态时也请求中断归一化，用于覆盖页面刷新或被丢弃但没有触发浏览器启动事件的场景。

页面根据检查点重建：

- CSV 文件信息和 URL 预览。
- `parsedUrls`、`localResults` 和计数。
- 当前进度与各结果筛选项。
- 用户上次的自动化设置和超时时间。
- 恢复提示及继续、终止、导出操作。

恢复不依赖用户重新选择原 CSV 文件。

## 数据流

### 开始任务

1. 用户上传 CSV 并点击开始。
2. `batch.html` 构造完整初始检查点并发送 `BATCH_SESSION_START`。
3. 后台持久化检查点，再调用 `requestKeepAwake('system')`。
4. 后台确认成功后，页面才打开第一个目标标签页。

### 处理单个项目

1. 页面发送领取任务命令，后台把任务从 `queued` 改为 `active`。
2. 页面创建标签页并发送 `BATCH_HANDLE`。
3. 内容脚本识别、生成并填写评论。
4. 自动提交前，内容脚本发送 `BATCH_TASK_SUBMITTING` 并等待成功响应。
5. 内容脚本点击提交并发送最终确认。
6. 后台原子地保存结果并把任务改为 `terminal`。
7. 页面收到确认后关闭标签页并领取下一项。

### 重启恢复

1. Chrome 启动，后台读取遗留检查点。
2. 后台归一化活动任务、把批次改为 `paused_recovery` 并确保没有保活请求。
3. 后台打开唯一恢复页。
4. 页面用检查点重建 UI。
5. 用户点击继续。
6. 后台把批次改为 `running`、申请系统保活并返回最新检查点。
7. 页面从第一个 `queued` 项继续。

## 错误处理

### Power API 调用失败

开始或继续任务时，如果 `requestKeepAwake('system')` 抛错，任务保持暂停，不打开新的目标标签页，并向用户显示“无法阻止系统休眠”。用户可以修复扩展权限或重新加载后重试。

释放保活失败不阻止终止或完成状态落盘，但必须记录诊断日志。后续后台启动时再次执行释放。

### 检查点写入失败

任务开始、领取下一项或进入提交阶段的关键写入失败时停止推进，并显示可重试错误。不得在检查点未成功记录的情况下继续点击提交。

### 标签页创建失败

该任务记录为 `fail` 终态，保存错误信息，然后继续下一个 `queued` 项。

### 重复或延迟消息

后台按 `batchId + urlIndex` 校验，并拒绝修改已经 `terminal` 的任务。结果消息重复到达时不得重复统计或覆盖首次终态。

### 用户手动关闭工作标签页

若任务仍为 `active`，记录为失败。若已经进入 `submitting`，使用与重启相同的“可能已提交，请人工确认”终态，避免自动重试。

### 恢复数据损坏

检查点读取后先校验版本、批次身份、输入数组、任务索引和结果结构。无法安全恢复时不申请保活、不自动执行，并显示“恢复数据损坏”。原始存储保留，供诊断或手动清除。

## 测试策略

### 检查点状态机单元测试

- 创建检查点包含完整输入行且不截断。
- 只有 `queued` 任务可以变为 `active`。
- `active` 可以进入 `submitting` 或终态。
- `submitting` 收到确认后进入终态。
- 终态任务拒绝重复结果。
- 中断归一化把 `active` 恢复为 `queued`。
- 中断归一化把 `submitting` 转为一次性的 `manual_required`。
- 多次中断归一化结果不重复。
- 恢复游标指向第一个未完成任务。
- 完成和终止批次不能再次恢复运行。
- 损坏或不支持版本的检查点被拒绝。

### 电源管理单元测试

- 开始和继续任务请求 `system` 级别保活。
- 重复的运行消息不会产生不必要的重复状态变更。
- 暂停、终止和完成释放保活。
- 保活申请失败时任务不进入运行状态。
- Chrome 启动恢复不会自动重新申请保活。

### 后台消息与启动测试

- 检查点写入按顺序执行，不因并发消息丢失更新。
- 错误 `batchId`、越界索引和重复终态被拒绝。
- `onStartup` 只为未结束批次打开恢复页。
- 已存在 `batch.html` 时不重复创建。
- 完成或终止批次启动时不打开页面。

### 页面恢复测试

- 页面可从检查点重建 CSV 信息、队列、结果、统计和设置。
- `paused_recovery` 不自动打开目标网站。
- 点击继续后才申请保活和领取下一项。
- 点击终止后释放保活并保留可导出结果。
- 页面刷新后进入暂停恢复状态。
- 恢复不要求重新选择 CSV 文件。

### 回归验证

- 现有成功、失败、跳过、无评论框、非法站点和需人工处理结果仍正确统计。
- 正常完成后关闭工作标签页并释放保活。
- 手动终止后不再打开新标签页。
- 运行完整 `npm test` 测试套件。
- 在 Chrome 中手工验证：开始批次、显示器息屏后继续处理、强制退出 Chrome、重新打开、恢复页保持暂停、点击继续后从断点推进。

## 验收标准

- 任务运行期间，Chrome 的扩展后台持有 `system` 级别保活；显示器仍可按 macOS 设置关闭。
- 暂停、终止和完成后不再持有本批次的保活请求。
- 任意长度的当前批次均能从检查点重建，不受现有最近 100 条结果限制。
- Chrome 在至少完成一项、尚有未处理项时退出并重启，扩展自动打开一个恢复页。
- 恢复页完整展示原批次与已有结果，且不会自动打开网站或提交评论。
- 用户点击继续后，从第一个安全的未完成任务继续，不重复处理已有终态。
- 中断时处于提交阶段的项目只产生一个“需人工确认”结果，绝不自动重试。
- 重复启动、刷新或重复结果消息不会造成重复统计。
- 所有新增单元测试和现有回归测试通过。
