# 本地评论历史保存设计

## 背景

当前批量评论流程会把执行结果暂存在 `chrome.storage.local`：

- `background.js` 中的 `batchResults` 最多保留最近 100 条。
- `batch.js` 中的 `batchLocalResults.results` 也只保留最近 100 条。
- 已有记录包含页面 URL、执行结果、AI 文案、错误信息和时间，但缺少完整的推广网站、实际提交正文和结构化锚文本信息。
- 大数组形式的 `chrome.storage.local` 不适合长期保存和查询几十万条记录。

预计使用规模为：

- 每天约 20 个网站。
- 每个网站约 200 条成功评论。
- 每天约 4,000 条记录。
- 3 个月约 360,000 条记录，预计占用约 0.7–1.8 GB，实际占用取决于正文长度和索引数量。

## 目标

为每一条插件确认“提交成功”的评论建立可靠的浏览器本地历史：

- 保存提交时间、评论页面、目标域名、推广网站、实际评论正文。
- 解析并保存正文中所有 HTML `<a>` 标签的锚文本和链接。
- 在页面刷新、消息重发和扩展 Service Worker 重启时保证不重复。
- 支持按时间、网站和锚文本分页查询。
- 浏览器内默认保留最近 90 天。
- 到期前提醒用户导出；只有用户明确确认后才能删除。
- 支持大批量 CSV 归档。
- 不依赖本机 Node 服务或远程服务器。

## 非目标

- 不判断评论是否已被站长审核通过或最终公开。
- 不保存邮箱密码、Cookie、页面快照或完整页面 HTML。
- 不建立云端同步或多设备共享。
- 不在本次设计中实现通用全文搜索引擎。
- 不在浏览器中引入 SQLite/WASM。

## 术语和状态语义

`success` 沿用现有批处理语义：插件完成提交并收到当前导航或确认流程的成功回报。历史页面统一显示为“提交成功”，不能显示为“已发布”或“审核通过”。

只有 `result === "success"` 的任务进入评论历史。`skipped`、`fail`、`no_comment_box`、`manual_required` 和 `blocked_illegal` 不进入成功历史。

## 技术方案

采用 Chrome 扩展 Origin 下的 IndexedDB 作为主存储，并在 `manifest.json` 中增加：

- `unlimitedStorage`：解除 `chrome.storage.local`、IndexedDB 和 OPFS 的常规容量与驱逐限制。
- `alarms`：每天执行一次保留期检查。
- `notifications`：显示系统归档提醒。

`background.js` 是唯一写入入口。新增独立的评论历史数据库模块，封装：

- 建库和版本迁移。
- 成功记录写入和幂等更新。
- 索引查询和分页。
- CSV 导出游标。
- 保留期计算。
- 经确认后的事务删除。
- 归档摘要记录。

内容脚本只负责采集和上报，不直接操作评论历史数据库。批处理页和新的评论历史页只通过扩展消息调用后台服务。

## 数据流

### 成功记录写入

1. `content.js` 在真正触发评论提交前读取评论框的当前值。
2. 采集当前评论页面 URL、推广网站 URL、批次 ID、任务序号和提交时间。
3. 从实际提交正文中解析全部 `<a>` 标签。
4. 现有提交确认流程向 `background.js` 发送 `BATCH_HANDLE_CONFIRM`。
5. `background.js` 仅在结果为 `success` 时开启一个同时覆盖评论和锚文本对象仓库的 IndexedDB 事务。
6. 使用 `batchId:urlIndex` 作为稳定记录 ID，重复消息执行 UPSERT，不新增重复记录。
7. 事务成功后，后台发送带有 `historySaveStatus = "saved"` 的
   `BATCH_CONFIRMED`，由批处理页更新界面并关闭目标标签页。事务失败时按下述待重试流程处理。

需要调整现有消息载荷，使其传递“提交时实际正文”而不只传递 AI 最初生成的 `aiContent`。AI 文案可作为调试来源保留在短期运行结果中，但评论历史以实际提交值为准。

### 写入失败和重试

如果 IndexedDB 写入失败：

1. 将完整记录以 `historyPending:<recordId>` 为独立键写入 `chrome.storage.local` 待重试队列，避免每次重写一个不断增长的大数组。
2. 批处理结果显示“评论已提交，但历史记录保存失败”。
3. 在浏览器启动、批处理页打开、评论历史页打开或下一次成功提交时重试。
4. 重试继续使用相同稳定 ID，成功后从队列移除。
5. 如果主写入和待重试队列写入都失败，必须显示不可忽略的错误和未保存数量，不得静默丢弃。

`unlimitedStorage` 同时作用于待重试队列，但该队列只作为异常恢复机制，不能作为长期主存储。

待重试记录成功写入 `chrome.storage.local` 后，后台仍发送带有
`historySaveStatus = "queued"` 的 `BATCH_CONFIRMED`，允许批处理页关闭目标标签页。
正常写入 IndexedDB 时该字段为 `saved`。主写入和待重试队列都失败时该字段为
`failed`，批处理页必须保留一条不可忽略的未保存错误。

## IndexedDB 数据模型

数据库名称：`auto_comment_history`

初始版本：`1`

### `comment_records`

一条成功评论对应一条主记录。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | 主键，格式为 `batchId:urlIndex` |
| `batchId` | string | 批次 ID |
| `urlIndex` | number | 批次内任务序号 |
| `submittedAt` | number | 实际提交时间，Unix 毫秒 |
| `archiveMonth` | string | 按提交时浏览器本地时区计算的月份，格式 `YYYY-MM` |
| `targetPageUrl` | string | 发表评论的具体页面 |
| `targetDomain` | string | 规范化后的目标页面域名 |
| `promotedWebsiteUrl` | string | 提交时配置的推广网站地址 |
| `promotedDomain` | string | 规范化后的推广网站域名 |
| `commentHtml` | string | 评论框中实际提交的完整值 |
| `commentText` | string | 去除 HTML 并规范化空白后的纯文本 |
| `submitStatus` | string | 固定为 `submitted` |
| `source` | string | `live` 或 `legacy` |
| `createdAt` | number | 本地首次写入时间 |
| `updatedAt` | number | 最近幂等更新时间 |

索引：

- `by_submitted_at`：`submittedAt`
- `by_archive_month`：`archiveMonth`
- `by_target_domain`：`targetDomain`
- `by_promoted_domain`：`promotedDomain`
- `by_batch_task`：`[batchId, urlIndex]`，唯一

主键已经能够保证幂等；唯一复合索引用于验证数据一致性和兼容未来记录 ID 规则升级。

### `comment_anchors`

每个 HTML `<a>` 标签对应一条锚点记录。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | 主键，格式为 `commentId:position` |
| `commentId` | string | 对应的评论主记录 ID |
| `position` | number | 在正文中的出现顺序，从 0 开始 |
| `anchorText` | string | 规范化空白后的可点击文字 |
| `anchorTextNormalized` | string | 用于查询的小写规范化文本 |
| `hrefRaw` | string | HTML 中的原始 `href` |
| `hrefResolved` | string | 相对评论页解析后的绝对地址；无法解析时为空 |
| `hrefDomain` | string | 规范化后的链接域名；无法解析时为空 |

索引：

- `by_comment_id`：`commentId`
- `by_anchor_text`：`anchorTextNormalized`
- `by_href_domain`：`hrefDomain`

一条评论没有 HTML 链接时，不创建锚点记录，但仍保存评论主记录。

解析 HTML 时使用不执行脚本的 DOM 解析方式。历史页面必须用 `textContent` 或等价安全方式显示保存内容，不能把保存的 `commentHtml` 直接注入 DOM。

### `archive_events`

只保存不含评论正文的归档和删除摘要。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | 归档事件 ID |
| `rangeStart` | number | 本次范围开始时间 |
| `rangeEnd` | number | 本次范围结束时间 |
| `recordCount` | number | 记录数量 |
| `fileNames` | string[] | 生成的 CSV 文件名 |
| `exportStartedAt` | number | 用户开始导出的时间 |
| `deleteConfirmedAt` | number | 用户确认删除的时间 |
| `deletedAt` | number | 删除事务完成时间 |

### `history_meta`

保存数据库版本、旧数据迁移标记、最近保留期检查时间和最近提醒时间。提醒去重以到期记录集合及提醒时间为依据，避免 Service Worker 重启后连续弹出相同通知。

## 锚文本解析规则

- 解析正文中全部 `<a>` 标签，而不是只取第一个。
- `anchorText` 使用元素可见文本并合并连续空白。
- 同时保存原始 `href` 和基于评论页面解析的绝对 URL。
- 允许同一正文出现重复锚文本或重复链接，使用 `position` 保留原顺序。
- 空锚文本仍保存，便于识别图片链接或异常 HTML。
- 无效 URL 不导致整条评论保存失败；保留 `hrefRaw`，并将 `hrefResolved` 和 `hrefDomain` 置空。
- 兼容 `href` 中现有提示词要求产生的真实换行。

## 评论历史页面

新增独立评论历史页面，提供：

- 总记录数、最近 24 小时记录数和预计磁盘占用。
- 按提交日期范围筛选。
- 按目标网站域名筛选。
- 按推广网站域名筛选。
- 按锚文本前缀或锚链接域名查询。
- 分页显示，每页 50–100 条，不一次加载全部数据。
- 查看完整评论正文和全部锚链接。
- 导出选定时间范围。
- 查看即将到期、等待确认删除以及历史归档摘要。

IndexedDB 不提供通用全文搜索。本版本不对 360,000 条正文执行无索引的全库包含搜索。后续确有需要时再单独设计倒排索引。

## 保留、提醒和确认删除

保留期采用滚动 90 天，而不是按自然月粗略删除。

- 记录年龄达到 80 天时进入“即将到期”，首次提醒用户。
- 第 87 天再次提醒。
- 年龄达到 90 天时进入“等待确认删除”并立即提醒。
- 90 天后仍未处理时，每 7 天再次提醒。
- 未经用户确认，定时任务绝不删除记录。
- 用户忽略提醒时，数据继续保留并在批处理页和评论历史页显示常驻横幅。
- 界面同时展示当前记录数和 `navigator.storage.estimate()` 提供的占用估算。

删除流程：

1. 用户在年龄已达到 90 天的记录中选择待清理范围并点击“导出待清理记录”。
2. 系统生成 CSV 文件，并显示数量、时间范围和文件名。
3. 界面显示“我已完成归档，确认删除”按钮。
4. 用户再次确认。
5. 后台在同一个事务中删除对应 `comment_records` 和 `comment_anchors`，并写入 `archive_events` 摘要。
6. 只有整个事务成功后，界面才显示删除完成。

导出动作不等同于确认删除。即使浏览器已经开始下载，仍必须由用户单独确认。

系统通知和页面横幅用于提醒，不要求用户立即处理，也不阻止新的批量评论任务。

## CSV 归档

CSV 使用 UTF-8 BOM，便于 Excel 正确识别中文。

每条评论占一行，至少包含：

- 提交时间
- 评论页面 URL
- 目标域名
- 推广网站 URL
- 推广网站域名
- 完整评论 HTML
- 评论纯文本
- 锚文本数组
- 原始锚链接数组
- 解析后锚链接数组
- 批次 ID
- 任务序号

多个锚点字段使用 JSON 数组字符串写入单元格，保证锚文本和链接的顺序及对应关系不会丢失。

单个 CSV 最多包含 50,000 条记录。超过上限时按提交时间顺序拆分，文件名示例：

```text
comment-history-20260701-20260731-part-001.csv
comment-history-20260701-20260731-part-002.csv
```

导出必须：

- 正确引用逗号、双引号、回车和换行。
- 对可能触发 Excel 公式执行的单元格进行防护。
- 使用 IndexedDB 游标分批读取，避免一次将全部选定记录加载到内存。
- 在页面显示导出进度和已完成文件数。

## 旧数据迁移

首次升级时读取现有 `batchResults` 和 `batchLocalResults`：

- 只迁移 `result === "success"` 的记录。
- 以批次 ID 和任务序号去重。
- 旧记录的 `aiContent` 作为历史正文迁移，并标记 `source = "legacy"`。
- 从旧正文解析能够识别的锚文本。
- 无法可靠确定的推广网站地址保持为空，不使用当前配置猜测历史值。
- 迁移成功后写入版本标记。
- 初次发布不立即删除原有 `chrome.storage.local` 数据；待新数据库稳定后在后续版本清理。

迁移是幂等的，扩展中断后可以安全重新执行。

## 数据一致性和安全

- 评论主记录和全部锚点必须在同一个 IndexedDB 读写事务中提交。
- 幂等更新主记录时，先删除该评论原有锚点，再写入当前解析结果，避免残留锚点。
- 删除评论和锚点使用同一个事务。
- 数据库升级失败时保留旧数据库并停止新写入，不能自动删库重建。
- CSV 导出防止公式注入。
- 历史页面不执行保存的 HTML。
- 不记录邮箱密码、Cookie 或站点认证信息。
- 设置页明确说明卸载扩展会删除 IndexedDB，重要数据需要归档。

## 性能策略

- 所有列表查询必须走索引和游标分页。
- 每页默认 50 条，最多 100 条。
- 统计数据可以增量维护或按索引游标分批计算，不能每次打开页面全表加载。
- CSV 使用游标分块读取，并按 50,000 条拆分文件。
- 大范围删除按确定的记录 ID 分块准备，但最终每一删除块保持主记录和锚点事务一致。
- 提交路径只执行一次小型 IndexedDB 事务，不等待统计重算或归档检查。

## 测试

### 单元测试

- 稳定 ID 和重复消息幂等。
- 实际评论正文优先于 AI 初始文案。
- 多个锚点、重复锚点和空锚文本。
- 相对 URL、绝对 URL、无效 URL、HTML 实体和换行 `href`。
- 域名规范化。
- 79、80、89、90 天的保留期边界。
- 提醒间隔和提醒去重。
- CSV 引号、逗号、换行、中文、JSON 数组和公式注入防护。

### 集成测试

- `BATCH_HANDLE_CONFIRM success` 写入一条完整历史。
- 非成功结果不写入历史。
- 写入完成后才发送 `BATCH_CONFIRMED`。
- 页面刷新和 Service Worker 重启后补发确认不重复。
- 写入失败进入待重试队列，重试成功后自动清除。
- 数据库版本升级失败不删除旧库。
- 未经用户确认，定时保留期检查不会删除任何记录。
- 用户确认后主记录和锚点同时删除。
- 旧 `chrome.storage.local` 成功记录幂等迁移。

### 规模和人工验证

使用 360,000 条模拟记录验证。性能测试记录 Chrome 版本、操作系统、硬件、
数据库冷热状态，并在同一基准环境连续运行 5 次：

- 历史首页和索引筛选的 5 次中位数不超过 2 秒；该指标是基准目标，发布记录需附测试环境。
- 分页不会一次加载全库。
- 提交写入不会使批处理流程产生明显停顿。
- 大范围导出按 50,000 条拆分并持续显示进度。
- 导出或删除过程中关闭页面后，数据库仍保持一致。
- Chrome 系统通知和页面横幅能够正确跳转到待处理记录。

## 验收标准

- 每个插件确认成功的任务最多对应一条历史记录。
- 保存的是提交时评论框中的实际正文。
- 所有 HTML 锚文本和链接按原顺序保存。
- 失败、跳过和人工处理任务不混入成功历史。
- 90 天前不会进入待删除状态。
- 未经用户明确确认，任何路径都不能删除历史记录。
- 导出文件能够在 Excel 中正确打开且不会执行评论内容中的公式。
- 360,000 条记录下仍能分页和使用索引筛选。
- 写入失败对用户可见并可以自动重试。
- 卸载风险和导出入口对用户清晰可见。
