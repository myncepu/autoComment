# 批次单项超时与结果预览设计

## 背景

批处理向导已经允许设置 `timeoutSeconds`，但当前 worker 生命周期仍可能被长时间未完成的
`BATCH_HANDLE` 响应拖住。目标标签页关闭后，checkpoint 也可能短暂保留 active 状态，
控制台便继续使用当前时间计算耗时，出现任务已结束但耗时仍增长的问题。

当前队列表格只显示目标 URL、状态、耗时、阶段/错误和 worker 标签页。用户还需要直接
辨认每条任务实际使用的评论文本、锚文本和推广网站，并在内容过长时方便查看完整值。

## 目标

- 每条任务使用批次设置中的独立页面超时，超时后可靠终止并释放并发槽位。
- 目标标签页被关闭、任务成功、失败、超时或转人工处理后，耗时立即冻结。
- `BATCH_HANDLE` 只确认内容脚本已经接受任务，不等待整段页面自动化完成。
- 队列表格显示评论文本、锚文本和推广网站的安全结果快照。
- 长文本默认截断，鼠标悬停和键盘聚焦都能查看全文。
- 响应式窄屏保留关键信息，并把完整结果放入任务详情。
- 不把密码、API Key、Cookie、页面令牌或其他密钥加入 checkpoint、消息、历史或界面。

## 采用方案

采用结果快照方案。任务确认时从已经捕获的评论历史中提取以下展示字段，并随终态结果
安全落盘：

```js
{
  commentText: '实际评论纯文本',
  anchorTexts: ['锚文本 A', '锚文本 B'],
  promotedWebsiteUrl: 'https://promotion.example/'
}
```

`aiContent` 继续保留以兼容旧批次。`commentText` 优先使用实际捕获的评论纯文本，缺失时
回退到 `aiContent`。`promotedWebsiteUrl` 优先使用实际捕获的推广链接，缺失时回退到该
任务冻结的 Promotion Site 快照。旧 checkpoint 没有这些字段时保持可读，不猜测不存在
的历史锚文本。

没有采用运行时逐行查询 IndexedDB 历史记录的方案，因为它会让控制台渲染依赖异步历史
服务，并让离线恢复和旧结果显示不稳定。也没有采用只从 AI 文案临时解析的方案，因为
生成内容不等于实际提交内容，锚文本可能不准确。

## 单项超时

### 截止时间

每个 opening reservation 和 active worker 都有独立截止时间：

```text
deadline = task startedAt + timeoutSeconds * 1000
```

页面刷新或控制台恢复时使用 checkpoint 中冻结的 `startedAt` 重新计算剩余时间，不重新
获得完整时长。设置变更只影响新批次，运行中的批次继续使用已冻结设置。

运行时保留低频一致性扫描作为恢复兜底，但正确性由每任务截止计时器保证，不依赖一个
可能被页面节流的共享轮询。

### 超时终态

截止时间到达后：

1. 以任务身份 `batchId + urlIndex + attempt` 抢占唯一 finalizer。
2. 检查提交上下文；若已进入提交但结果不明确，转为 `manual_required /
   submission_uncertain`。
3. 否则写入 `fail / task_timeout`。
4. 终态事务记录固定 `elapsed`。
5. 关闭 worker 标签页并释放槽位。
6. 调度下一条排队任务。

迟到的内容脚本响应或确认不能覆盖已经完成的终态。

### 页面被关闭

`tabs.onRemoved` 对非预期关闭立即使用同一个 finalizer。提交前关闭记录明确失败；提交
确认期间关闭记录为需人工确认。无论哪种结果，任务不再保持 active，耗时随终态冻结。

## 内容脚本接收契约

内容脚本收到合法 `BATCH_HANDLE` 后同步返回：

```js
{ ok: true, accepted: true, urlIndex }
```

自动化流程随后异步执行，并通过现有 phase/confirmation 消息更新状态。同步响应只表示
消息已接收，不表示任务已完成。

`BATCH_HANDLE` 同时携带非敏感自动化开关快照：

```js
{
  automation: {
    autoGenerate: true,
    autoSubmit: false,
    autoOpenPanel: false
  }
}
```

当 `autoSubmit` 为 false 时不得点击提交按钮、不得创建 submitting 上下文。生成并填充
完成后写入 `manual_required`，供用户从控制台人工处理。该契约不包含 Profile 密码。

## 队列表格

桌面表格增加三列：

- 评论文本：实际评论纯文本，缺失时显示 `—`。
- 锚文本：多个锚文本用 `、` 连接，去重后显示。
- 推广网站：显示实际推广域名或 URL。

单元格使用固定最大宽度、单行省略号和可聚焦文本元素。完整内容同时写入可访问名称，并
通过统一浮层在 hover 或 focus 时展示；不能只依赖浏览器原生 `title`。按 Esc 或移开
焦点关闭浮层。

在窄屏卡片布局中显示评论摘要和推广域名，锚文本及所有完整值保留在任务详情抽屉。
详情抽屉增加“评论文本”“锚文本”“推广网站”字段。

队列关键字搜索同时覆盖这三个字段。

## 多推广网站兼容

本设计不重新定义多网站领域模型。它消费已完成的多身份/多推广网站契约：

- Promotion Site 使用稳定 `promotionSiteId`。
- 每条任务冻结 `profileId + promotionSiteId` 及非敏感快照。
- 设置页支持多个 Promotion Site 的新增、编辑、启停。
- 批次使用默认组合、确定性加权组合或 CSV 显式分配。
- 旧单推广网站设置自动迁移为默认 Promotion Site。

结果预览优先展示任务实际捕获的链接，并回退到冻结的 Promotion Site 快照，因此不会
因用户后来修改设置而改变旧批次显示。

## 错误与恢复

- 计时器回调失败时暂停批次进入恢复状态，并保留可达的 worker 所有权。
- 关闭标签页失败时不伪造终态完成，控制台显示恢复错误。
- 终态结果缺少新展示字段时以空值兼容，不阻止加载或导出。
- 所有展示字段经过长度限制、URL 凭据拒绝和诊断文本清洗。
- UI 始终通过 `textContent` 创建文本，不解释评论 HTML。

## 测试与验收

自动化测试按 TDD 覆盖：

- 每任务截止计时器使用设置值并在到期后终态化、关闭标签页、补充队列。
- opening、active、submitting 和意外关闭的竞态只有一个终态。
- 迟到的 handle/confirmation 不覆盖 timeout。
- 终态行在不同 `now` 值下保持相同 `elapsedMs`。
- `BATCH_HANDLE` 同步确认，自动化异步执行。
- `autoSubmit: false` 从不点击提交并转人工处理。
- 安全结果快照的规范化、长度限制、旧 checkpoint 兼容和敏感字段拒绝。
- 三个新字段的表格截断、键盘焦点全文浮层、详情、搜索和 1440/1024/640 响应式布局。

真实 Chrome 验收仅使用本地 HTTP fixture：

1. 加载未打包扩展并重新加载。
2. 导入 5 条本地 URL，并发数设为 3。
3. 设置短超时，让一个 fixture 故意挂起，确认准时关闭并继续队列。
4. 完成其他任务后等待，确认终态耗时不再变化。
5. 验证评论文本、锚文本、推广网站的截断、hover、focus 和详情全文。
6. 验证 `autoSubmit: false` 不产生提交请求。

不得使用第三方评论网站进行提交验收。
